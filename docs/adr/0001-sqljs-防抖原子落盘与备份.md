# ADR-0001: 数据库持久化采用 sql.js + 防抖原子落盘，不迁移 better-sqlite3

日期：2026-08-28 ｜ 状态：Accepted ｜ 决定人：AI 建议，用户默认（scope.md 末条）

## 背景

初版部署时 better-sqlite3 在服务器编译失败，改用 sql.js（WASM，全内存）。原始实现每次写操作全量 `db.export()` + `writeFileSync`：写放大 O(全库)，且非原子——进程中途被杀可能损坏库文件，且无任何备份。

## 备选评估

1. **迁移 better-sqlite3**（原编译失败的方案）：同步 API 最优、写放大最小。代价：需重新解决原生编译问题（当年失败原因未复现验证）、有停机迁移窗口、偏离"共享服务器不换引擎"铁律。
2. **维持现状**（每次写全量落盘）：零改动，但数据损坏风险与写放大随数据量增长恶化。
3. **sql.js + 防抖合并 + 原子 rename + 双备份**（选定）：保留 sql.js 零编译依赖；写放大从"每次操作"降为"每 500ms 合并"；临时文件 + fsync + rename 保证任何时刻磁盘上是完整库；每日双目录备份兜底数据安全。

## 决策

选 3。实现于 `server/db.js`（`scheduleFlush`/`flushNow`/`backupDb`），恢复工具 `scripts/restore.js`。

## 后果

- 收益：崩溃安全、写压力可控、有恢复路径。
- 代价：全内存（库体积受内存约束）、崩溃瞬间最多丢 5 秒写入、备份是全量拷贝。
- **重评触发**：库文件 > 50MB 或写 QPS 明显上升时，重新评估迁移 better-sqlite3（迁移脚本需另行编写与演练）。
